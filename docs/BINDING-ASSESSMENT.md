# 双人绑定与共享内容 — 评估分析 (BINDING-ASSESSMENT)

- 日期: 2026-09-30 ｜ 版本: v2.1 规划评估 ｜ 状态: 评估完成，技术选型待 BaaS 调研回充
- 触发: 用户需求"一人注册后另一人绑定，互相查看内容"

---

## 1. 这个需求值不值得做？——值得，它是产品成人礼

**价值评估（用户视角）：**

| 维度 | 单机版（现状） | 绑定版 |
|---|---|---|
| 递台阶 | 递手机给对方（同框限定） | **异地可递**——TA 打开就看到"我想和好"，这正是盲评 C 说的"异地场景断裂"的解药 |
| 想你了 | 自己手机计数（对方看不到） | 对方手机亮一下"TA 想你了 ×3"——异地恋核心需求（调研需求清单第 5 条"没话说"的解药） |
| 今日需要 | 同框可见 | 异地可见——"今天我需要……"直达对方 |
| 小事清单 | 两人在同一设备点亮 | 异地也能共同推进（一人点亮一处，进度同步） |
| 恋爱天数 | 本机记录 | 双端一致，不会"各自记的不一样" |

**结论**：绑定把产品从"同框玩具"升级为"异地恋刚需工具"——而异地恋正是大学生情侣的核心场景（调研：分手主因之一、"没话说"是高频痛点）。这个需求的真实性无需怀疑。

**但要清醒**：它同时带来产品最重的三项负担——后端运维、隐私责任、分手退出设计。见第 4 节。

## 2. "互相查看哪些内容"——共享范围设计（核心产品决策）

原则（继承既有的主权哲学）：**共享的是"我主动给你的信号"，永远不是"你的全部数据"。**

| 内容 | 共享？ | 设计 |
|---|---|---|
| 💭 想你了 | ✅ 实时共享 | 对方打开/收到提醒即见计数 |
| 🪜 递台阶 | ✅ 双向核心 | 递出→对方"接住/晚点说"回执，全程双向 |
| 🗓 今日需要 | ✅ 共享 | 双方各自的今日需要互相可见（这正是它的存在意义） |
| 🗓 小事清单进度 | ✅ 共享 | 共同点亮的进度条双端一致 |
| 🏆 成就/连击/气候 | ✅ 共享 | 共同的数字，共同的荣耀 |
| 🎬 剧本与演出记录 | ✅ 共享 | 剧场是两个人的 |
| 📊 需求体检条 | ⚠️ **半共享（自报才可见）** | 我标的状态我公开；未公开（免检）则对方只见"TA 今日免检"，永远不见数值 |
| 🛡️ 免战牌使用 | ❌ 只显示"TA 打了免战牌"这一事实本身，次数不可见（不追问原则的延伸） |
| 💛 夸夸内容 | ✅ 收到的可见；我写下的草稿不可见 |
| 📝 日志感想 | 🔘 每条可选"共享/私密"（默认私密——给不想让对方看到的情绪留位置） |

**反查岗红线**（调研雷区 2：定位/越权监控必死）：不采集位置、不上传相册、不做"对方在线状态/已读回执"、不推送"TA 打开过 X 次"类监控数据。

## 3. 绑定机制设计（零注册）

```
① 一人点「创建我们的小剧场」→ 生成本机匿名 ID + 6 位房间码（如 7K2Q9F，48 小时有效）
② 把码发给对方（微信/QQ 随意）
③ 对方输码「加入」→ 两人同房间的数据互相可见
④ 分手/退出：任一方「解除绑定」→ 对方确认 → 双端本地数据可各自选择"删除/留作纪念"
```

- 无手机号、无实名、无头像昵称上传——只有匿名 UUID + 房间码
- 换手机：用"房间码+恢复码"找回（或接受丢失，数据本来极轻）
- **分手设计是核心不是附属**（调研雷区 5：解绑困难是强负面记忆点）：解绑后双方本地数据完全自主，云端房间数据 30 天后自动清空；绝不出现"和前任注销不了关系"

## 4. 诚实的负担与风险

1. **后端运维责任**：一旦上云，数据丢失=情感事故。需要可靠的免费/低成本 BaaS（技术调研 agent 查证中：Supabase/Firebase/LeanCloud/Cloudflare 的 2026 免费额度与国内可达性）
2. **中国大陆可达性**：GitHub Pages 本身在国内就不稳定；后端若也在境外，大学生场景基本不可用。**这是选型的生死项**
3. **免费层跑路风险**：免费额度政策变动史（各云厂商都有先例）；需设计"导出逃生门"（随时一键导出全部数据为文件）
4. **关系数据的敏感级别**：情侣互动数据属于高敏个人信息。最小化采集（无手机号/无位置/无照片上云——照片留在本地）+ 一键删除是底线
5. **分手场景的伦理**：数据删除要"温柔且彻底"——这既是伦理也是产品机会（"和平分手包"可以做成有温度的功能而非技术附录）

## 5. 分阶段建议

- **阶段 1（绑定 MVP）**：房间码绑定 + 三样核心共享（想你了/递台阶/今日需要）——这三样是异地恋刚需且数据极轻
- **阶段 2**：小事清单/成就/气候同步 + 日志感想共享开关
- **阶段 3**：导出/实体化管道（呼应商业化调研：日志→纪念书）
- 本地模式**永久保留**：不上云的情侣依然可以完整使用（单机版已是合格产品）

## 6. 待决策点（需要用户拍板）

1. 后端选型（等 BaaS 调研回充：免费额度/国内可达性/账号归属——**可能需要用户注册一个云服务账号**）
2. 数据上云的隐私接受度（本机模式永久保留作为退路）
3. 阶段 1 范围确认（建议：只做三样核心共享）

## 7. 技术选型结论（BaaS 调研 agent 2026-09 查证回充）

| 方案 | 免费额度 | 国内直连 | 判定 |
|---|---|---|---|
| **Cloudflare Workers + D1** | 10 万请求/天；D1 读 500 万行/写 10 万行/天 | workers.dev 被墙；**绑自有域名后可达**（域名 10-60 元/年） | ✅ **主方案** |
| Supabase | 2 项目/500MB/无限 API；**7 天不活跃暂停**（可恢复） | 直连不稳定，需实测 | ✅ 备选（完全零成本路线） |
| Firebase | — | googleapis 被墙 | ❌ 排除 |
| LeanCloud 国内版 | 需手机号+实名+备案域名 | 好 | ❌ 违背零注册 |
| LeanCloud 国际版 | — | 共享域名 2022 起停止对大陆服务 | ❌ 鸡肋 |
| 腾讯云 CloudBase | 免费层 2022-08 取消，19.9 元/月起 | 好 | ❌ 月费违背零成本 |

- 写量核算：每对情侣每天 <50 条写，D1 免费写额度可容纳数千对
- 身份机制：**6 位房间码 + 匿名 UUID**（与微信情侣空间的"邀请码"闭环等价，无手机号）
- 跑路风险史已核实（LeanCloud 收紧/CloudBase 取消免费/jsonbin 一次性额度）→ 必须有"一键导出数据"逃生门
- 未能核实项：Supabase 大陆直连延迟精确值（上线前需在目标校园网络实测）

## 8. 实现记录（v2.1 绑定 MVP 已部署 2026-09-30）

- 用户拍板：先 GitHub 静态托管，不开付费服务 → 采用**零后端过渡方案**：同步码机制（生成文本包→微信发对方→粘贴导入合并，按事件 id 幂等）
- 新增 js/binding.js：房间（UUID）/匿名玩家（UUID）/6 位邀请码/事件日志（miss/need/repair/repair_ack/thing）/同步码 DRAMA1S 打包导入/对方状态投影（只投影共享白名单）/解绑
- 未来接 Cloudflare D1/Supabase：仅替换 genSync/importSync 为自动拉取，事件模型与 UI 不变
- 过程修复 4 处：严格模式块级作用域（挂载移至导出后）/UTC 时区（本地日期）/miss 快照语义（取 payload.count 最大值）/join 跨房污染（干净开始）
- 测试：binding 7 项 + data-engine 15 项 = 22/22；浏览器全流程（创建→邀请码→想你了→同步码）
- 定位声明：单机模式永久保留；绑定是增强。同步码为过渡，未来 BaaS 自动同步后此流程消失

## 9. 云同步实现记录（v2.1.1 已部署 2026-09-30）

- 用户拍板：先 GitHub 跑通自动同步 → **GitHub 秘密 Gist 作后端**（gh CLI 全自动创建：d29296d1…）
- 新增 js/github-sync.js 传输层：fetchGist（匿名可读）/ patchGist（需 token）/ pullMerge（幂等合并进本地）/ push（读-改-写全量房间）/ startAuto（30 秒轮询）
- **token 安全模型**：token 由用户在页面粘贴、只存本机 localStorage，绝不进源码/仓库/日志；Gist ID 硬编码（秘密 Gist URL 不可枚举）；提供"停用并清除"入口
- 真实验证（GitHub 真实后端）：页面创建小剧场+想你了 → syncNow → 云端出现房间与事件（gh api 核对）✅；云端注入对方事件（想你了×2+今日需要）→ 页面拉取后"TA 的状态"全部正确显示 ✅
- 并发写冲突缓解：push 前强制重读合并（读-改-写窗口极小）；后续可加 etag 乐观锁
- 大学生正式发布时的路线：此 GitHub 后端仅用于你们自用测试；国内公开发布需迁国内可达后端（CloudBase 付费档/自建），数据结构不变

## 10. 需求生命周期状态机（v2.2.1 已部署 2026-10-01）

- 用户需求：未被回应的需求后续更高概率出现；被抽到后发现已满足→满足卡标记并自动补抽
- 裁决与实现：回应卡本就 100% 置顶（不存在"抽不到"），"概率提升"翻译为**等待天数可视化**（"TA 已经等了 N 天"——柔软的存在感非惩罚计数）；新增需求状态机 **active → acked / fulfilled / skipped** + 回应卡三按钮（💛 我来回应 / ✅ 已经满足了 / [TA 撤回]）；需求主人侧完整状态显示（等待中/被回应/已完成/已跳过）
- 事件流扩展：need_fulfilled / need_skipped（need_ack 已有）
- 真实验证：页面标需要→对方 fulfilled→需求主人侧显示"✅ 已完成——线下做到了也算数" ✅

### 交叉矛盾（同功能不同画像互相打架）

| 功能 | A1 异地 | A2 同居 | 矛盾 | 裁决 |
|---|---|---|---|---|
| 定位文案 | 要"异地也能用" | 要"同框递着用" | 两种定位互斥 | ✅ 已统一为"同框递着用 · 绑定后异地同步" |
| 充能建议 | "一起散步"异地不可执行 | 同居可执行 | 单一文案无法两全 | ✅ 加异地版后缀 |
| 小事清单 | 校园锁定的部分无用 | A4 五年毕业用户一半锁定 | 非校园人群需要不同清单 | ⏳ 未来按"人生阶段"切换清单 |
| SOS 急救条 | A6 要求首屏第一眼 | A2 同居觉得"递手机"绕圈 | 首屏优先级冲突 | ✅ SOS 条首屏保留（同框递手机成本低，异地刚需更高） |

### 交叉矩阵裁决总结
产品哲学（反内卷/不追问/不翻旧账）在六个画像下均无矛盾；矛盾集中在**场景适配**（异地vs同框、校园vs职场）。已修的全部是 bug 级；A4 提出的"人生阶段切换"和 A1 提出的"异地模式开关"是 v2.3 同一方向——首启时问一次"你们是同城还是异地"，所有建议/卡池/清单联动。已记入未来项。
